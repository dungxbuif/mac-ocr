Repository onboarding

This guide gives a new engineer the shortest reliable path from a fresh checkout to a working OCR request. The repository contains one Go control/data plane, one native macOS OCR worker, local infrastructure helpers, and two static web builds.

Read these first​

  1. Local development to build and run the complete stack.
  2. Environment configuration before changing limits or credentials.
  3. API reference for the public contract.
  4. Technical design before changing storage, queueing, retention, or callbacks.
  5. Production deployment before preparing a release.

Important invariants​

  • Public clients may submit documents and read one known document ID. There is no public document list or user-controlled delete/cancel route.
  • Completed OCR payloads are read from Redis and expire with RESULT_TTL.
  • Terminal PostgreSQL document rows are temporary and are deleted after DOCUMENT_TTL.
  • Large uploads use an authenticated presigned URL and are size-checked before signing and again from stored object metadata/bytes before quota reservation.
  • PostgreSQL is authoritative for quota and lifecycle state. Redis is used for rate counters, caches, and TTL result serving.
  • Admin document listing is private control-plane functionality protected by an admin session and CSRF token.

Normal change workflow​

cd proxy
go test ./...
go vet ./...

cd admin-ui
npm ci
npm run build

cd ../../docs-site
npm ci
npm run build

Run scripts/prod_readiness_e2e.sh whenever a change touches authentication, uploads, quota, queueing, native callbacks, notifications, MCP, or retention.
